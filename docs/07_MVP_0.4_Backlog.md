# EXEL HELL — MVP 0.4 backlog

MVP 0.4 starts only after the MVP 0.3 graybox verdict. This file records known mechanic problems without silently expanding the current prototype scope.

## P0 — SUM(single cell) exploit

Current problem:

`SUM` of one numeric cell followed by a target behaves like a one-action CUT/PASTE.

This collapses the distinction between:
- `CUT/PASTE` = relocation;
- `SUM` = aggregation/compression.

Candidate fix already discussed:
- require at least 2 numeric source cells for SUM.

Do not implement before the current MVP 0.3 playtest pass is finished unless the exploit prevents a valid test.

## P0 — consuming SUM vs overlapping report goals

Current problem:

Some individually valid goals become mutually impossible because one consumes a token required by another.

Known blocked pairs:
- Salary Total + Salary of employee with max overtime;
- Salary Total + Salaries of employees with hours < 40;
- Bonus Total + Bonuses >= 4;
- Salary of employee with max overtime + Salaries of employees with hours < 40.

Candidate solution families discussed:

### A. Report-target SUM does not consume sources
No new player verb. SUM aimed at a Report Cell writes the answer but leaves source data intact.

Pros:
- smallest MVP 0.4 change;
- preserves overlapping report goals;
- no COPY/REF verb.

Cons:
- SUM has context-sensitive semantics depending on target type.

### B. Reference / `=` action
A Report Cell points at one source token instead of copying/moving it.

Pros:
- spreadsheet-native semantics;
- keeps consuming SUM clean;
- creates order-of-operations play around references and aggregation.

Cons:
- adds another core verb and expands scope.

### C. Non-consuming SUM everywhere
Simplest ruleset, but removes compression/destruction tradeoff that currently appears promising.

### D. Forbid overlapping goal combinations
Technically cheapest, but removes potentially interesting goal interference and is currently considered undesirable.

No choice is locked yet.

## P1 — DELETE usefulness under infinite #REF! outbreaks

Observation:

Once #REF! outbreaks became continuous, DELETE stopped being a way to defeat the threat and became only a local timing/geometry action.

Open question:
- is that local quarantine decision sufficiently useful;
- should DELETE be removed;
- or should it receive a clearer systemic role?

Do not invent a DELETE rework until playtests show whether players actually choose it in meaningful situations.

## P1 — SORT positional semantics

Previously discussed MVP 0.4 direction:
- make position of FieldKey / RecordKey affect ordering/projection;
- moving keys would therefore become structurally meaningful.

This is a new feature, not an MVP 0.3 fix. Only revisit if current core earns further depth.

## P2 — provenance / quality check

AggregateToken already retains source provenance metadata.

Current SUBMIT intentionally checks only the numeric answer: a correct number is accepted even if obtained by an unintended route.

Possible later uses:
- optional audit objective;
- hidden ending / perfect report;
- boss/manager quality requirement;
- scoring modifier.

Do not make provenance mandatory for normal report completion.
