# EXEL HELL — MVP 0.3 balance model

## Purpose

This model is a **playtest filter**, not a complete solver for the game.

We use it to answer one question:

> Does the current core become interesting when the peaceful optimal report route mathematically intersects the #REF! threat window?

Do not use it to exhaustively balance every state of the worksheet.

## Version boundary

- **MVP 0.3** = current playable graybox and balancing fixes required to test it honestly.
- **MVP 0.4** = future mechanic reworks/new verbs after the MVP 0.3 core verdict.

## Primary quantities

### Base Cost `C`

Minimum number of player actions required to solve a goal/goal combination without #REF! pressure.

For combinations, shared structural operations may reduce the sum of individual costs.

### Threat Horizon `H`

First-order approximation:

`H ≈ First Spawn Delay + Preferred Spawn Distance`

Current defaults:

`H ≈ 3 + 2 = 5`

This is intentionally approximate. Actual danger depends on current token positions, anomaly Intent, destroyed cells and later outbreaks.

### Threat Margin `M`

`M = H - C`

Working interpretation:

| M | Band | Meaning |
|---:|---|---|
| `>= +3` | SAFE | anomaly is probably irrelevant to the peaceful route |
| `+1..+2` | LIGHT | light pressure; route often finishes before serious contact |
| `0` | EDGE | route and threat arrive together |
| `-1..-2` | PRESSURE | player should need to adapt |
| `< -2` | OVERLOAD | likely mandatory firefighting / high failure rate |

These bands are hypotheses to calibrate through playtests.

## Data-level refinement

For important source token `i`:

- `U_i` = last turn when the peaceful plan still needs that token;
- `T_i` = first turn when #REF! can remove/block it;
- `Slack_i = T_i - U_i`.

`Slack_i <= 0` identifies a concrete point where the peaceful plan should collide with the threat.

We are not calculating exact `T_i` automatically yet. Use it for post-playtest analysis where needed.

Costs describe intended/meaningful routes, not exploits such as `SUM(single cell)`.

## Known impossible combinations in current MVP 0.3

These are **not balance failures**. They are structural conflicts created by current consuming SUM / direct-value handling and belong to the MVP 0.4 backlog.

- `ST + MS`
- `ST + LH`
- `BT + B4`
- `MS + LH`

Any triple containing one of these pairs is also blocked.

Do not spend playtest time on these combinations before MVP 0.4 resolves the underlying interaction.

## Current useful shared action

`OT + MS` can share `SORT Overtime`, reducing the naive combined peaceful cost by one action.

## Today's test matrix

Use these as a small spread across the pressure spectrum:

1. `ST + OT` — LIGHT
2. `ST + B4` — EDGE
3. `OT + MS` — EDGE; also tests shared structural work
4. `BT + MS` — PRESSURE
5. `ST + OT + BT` — PRESSURE; three simple goals composed together
6. `OT + BT + LH` — OVERLOAD stress test

The spreadsheet artifact contains all 35 combinations of 2–3 current goals and marks blocked/test combinations.

## What to record per run

- combination;
- win/loss;
- turns;
- first spawn cell;
- first turn where the peaceful plan changed;
- what #REF! forced the player to do;
- number of turns with 2+ reasonable choices;
- number of obvious/routine turns;
- report-solving fun 1–5;
- #REF! pressure fun 1–5;
- immediate replay desire 1–5;
- best moment;
- most irritating moment.

## Core verdict criterion

MVP 0.3 is promising if configurations around `EDGE/PRESSURE` repeatedly produce:

- readable consequences;
- meaningful route changes;
- failures attributable to player decisions rather than opaque spawn luck;
- desire to retry with a better order of actions.

If mathematically pressured configurations remain mostly routine, do not solve the problem by adding more features. Revisit the core before MVP 0.4 grows.
