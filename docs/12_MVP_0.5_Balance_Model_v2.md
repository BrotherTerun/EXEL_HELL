# EXEL HELL — FC2 multidimensional balance model v2

**Status: CURRENT authoring/smoke-test model.**  
This is not an exact solver. It rejects brittle layouts, separates useful workload from maintenance tax and tells us what must be verified in Unity.

Exact current L1–L4 baselines are mirrored in `balance/current_level_baselines.csv` and `balance/EXEL_HELL_FC2_Balance_Baselines.xlsx`.

## 1. Core cost

### `C_sem` — semantic lower bound
Minimum useful actions for the goal set under favorable geometry and sufficient formula inventory.

Current vocabulary lower bounds:
- SalaryTotal: 2;
- OvertimeTotal: 2;
- BonusTotal: 2;
- BonusAtLeastFour enum / current threshold `>=5`: 4;
- SalaryOfMaxOvertime: 3;
- SalaryForHoursBelowForty: 5;
- LowHours + OT Total + Bonus Total: 9.

### `C0` — legal authored baseline
Minimum **legal** no-REF turn-spending action count on the exact authored layout.

`C0` comes from an explicit route using current FC2 rules.

No legal route → `C0 = ∞` → level invalid.

### `C_spatial`
Extra useful geometry/manipulation actions beyond the semantic floor and pure formula tax.

Do not force a false exact decomposition when one MOVE serves multiple roles; annotate the route instead.

## 2. Report target mode

Every Report Goal should record one mode:

- `DirectValue` — plain ReportCell, deliver required Data token;
- `InlineSUM` — ReportCell + SUM, compute directly into report;
- `PlainDelivery` — plain aggregate ReportCell; compute elsewhere and MOVE Aggregate into it.

`PlainDelivery` is a current supported rule, not a validation error.

It usually adds one delivery MOVE versus an equivalent InlineSUM, but also frees the workspace formula for reuse. This is useful for controlled formula-scarcity experiments.

## 3. Formula Handling Load

Record:
- `F_act` — useful SUM+SORT activations;
- `F_move` — MOVE of empty FormulaCell;
- `F_extract` — MOVE removing an occupant to free formula;
- `F_delivery` — extraction that simultaneously achieves a required report delivery/staging objective.

Pure tax:

`F_tax = max(0, F_extract - F_delivery)`

Handling load:

`FHL = (F_tax + 0.5*F_move) / max(1,C0)`

Initial bands:
- `<0.10` light;
- `0.10..0.20` acceptable;
- `0.20..0.30` formula maintenance competes with puzzle;
- `>0.30` likely redesign.

### Scarcity gate
If a scarce formula inventory raises `C0` by >~35% over `C_sem` without a genuine placement/order/threat decision, add formulas or redesign.

A `PlainDelivery` MOVE that takes aggregate out of SUM and directly satisfies a ReportCell is `F_delivery`; it should not be counted as pure formula tax.

## 4. Formula placement choice

For each activation where relocation matters, define `P_i` = number of genuinely useful legal formula positions.

`PCI = mean(min(P_i,3)/3)`

Interpretation:
- `0..0.25` effectively predetermined;
- `0.25..0.50` limited choice;
- `0.50..0.75` healthy alternatives;
- `>0.75` many alternatives — verify position actually matters.

A movable formula with `P_i=1` is often just a fixed formula plus MOVE tax.

## 5. SORT spill pressure

For required SORT `j`:
- `L_j` spill length;
- for candidate placement `p`, `Block_jp` = minimum required clear/repair actions.

`SC_j = min_p(Block_jp)`

`Alt_j = count(p where Block_jp <= SC_j + 1)`

`SP_j = min(1, SC_j / max(1,L_j))`

Level diagnostics:
- `SP = mean(SP_j)` — obstruction;
- `SA = mean(min(Alt_j,3)/3)` — alternative richness.

## 6. MOVE/workspace pressure

- `M_filter` — required token/range MOVE actions for filtering/clearing/evacuation/geometry repair;
- `W_free` — initially useful free ordinary destinations excluding report/formula/mandatory future spill infrastructure;
- `W_peak` — maximum simultaneously staged/parked tokens.

`WP = W_peak / max(1,W_free)`

Bands:
- `<0.10` spacious;
- `0.10..0.25` normal;
- `0.25..0.40` constrained;
- `>0.40` staging scarcity may dominate.

Range MOVE counts destinations occupied, not one staged state per moved token action.

## 7. Goal dependency

For each goal `g`, source set `S_g`.

For pair `(a,b)`:

`J_ab = |S_a ∩ S_b| / |S_a ∪ S_b|`

Classify relation:
- independent;
- shared-prep;
- ordered;
- report-mediated;
- hard-conflict.

`report-mediated` means a ReportCell occupant may satisfy one goal and later be read persistently by another SUM.

This is true for a numeric occupant in either InlineSUM or PlainDelivery report cells.

Hard-conflict → `C0=∞` until layout/order/infrastructure changes.

## 8. Critical entity lifetime

Critical set `E` may include:
- raw Data token;
- key;
- aggregate;
- occupied FormulaCell with critical occupant;
- empty FormulaCell required later;
- critical spill/staging region.

For each `e`:

`U_e` = last baseline action index at which it must remain usable.

## 9. Threat arrival

Estimate earliest plausible anomaly contact:

`T_e = F + P_e`

where `F` is first outbreak delay and `P_e` is route/contact estimate including geometry.

Also record direct outbreak eligibility `O_e` when relevant.

Do not treat `T_e` as exact without a Unity trace. Spawn selection is dynamic and depends on current critical-token layout.

## 10. Slack / exposure

`S_e = T_e - U_e`

Interpretation:
- `>=3` comfortable;
- `1..2` manageable;
- `0` decision boundary;
- `-1..-2` forced reaction likely;
- `<=-3` overload candidate.

Level:
- `S_min = min(S_e)`;
- `Q = count(S_e <= 1) / |E|`.

Exposure bands:
- `<0.20` low;
- `0.20..0.40` light;
- `0.40..0.65` strong;
- `>0.65` systemic.

## 11. Recovery reserve

`B` = turn budget.

`R = B - C0`

Working bands:
- `R>=5` generous;
- `R=3..4` normal;
- `R=2` tight;
- `R<=1` brittle.

A level intended to teach threat should normally have enough reserve for at least one understandable recovery action.

## 12. Anomaly cadence

Let:
- `F` first outbreak;
- `A` active-outbreak delay;
- `Resp` respawn delay;
- `C0` baseline actions.

Approximate outbreak opportunities during baseline play:

`N_A = 0`, if REF disabled or `C0 < F`.

Otherwise:

`N_A = 1 + floor((C0 - F) / max(1,A))`

`AP = min(1, N_A/3)`

This counts outbreak windows, not every spread intent. Active corrupted cells may create additional tactical decisions between outbreaks.

## 13. Loss/recovery severity

`K_e` = minimum additional actions after threat/loss to restore a legal route.

Typical FC2 examples:
- pre-emptive raw token MOVE: ~1;
- empty FormulaCell evacuation: ~1;
- occupied FormulaCell + occupant evacuation: up to ~2;
- recomputable aggregate: recomputation route cost;
- destroyed irreplaceable required raw token: ∞;
- destroyed only remaining required formula infrastructure: potentially ∞.

`KS = mean(min(K_e,4)/4)` for finite values.

Any `K_e=∞` with `S_e<=1` is a catastrophic-exposure warning.

## 14. Puzzle Load

`C_n = min(1,C0/12)`

`M_n = min(1,M_filter/5)`

`PL = 100 * (0.45*C_n + 0.15*SP + 0.15*M_n + 0.10*DI + 0.10*WP + 0.05*FHL)`

Bands:
- 0..25 tutorial/light;
- 26..45 normal;
- 46..65 involved;
- 66+ high load.

`PCI`/`SA` are design gates/diagnostics, not direct difficulty weights.

## 15. Anomaly Threat

`SN = clamp((2-S_min)/5,0,1)`

`OR = count(O_e=1)/|E|`

`AT = 100 * (0.30*SN + 0.25*Q + 0.15*AP + 0.15*KS + 0.15*OR)`

Bands:
- 0..20 decorative;
- 21..40 light;
- 41..60 active tactical pressure;
- 61..80 severe;
- 81+ chaotic/catastrophic.

Do **not** publish precise AT for a new layout without inspecting actual Unity spawn/intent behavior. It is easy to manufacture false precision from guessed `T_e`.

## 16. Combined summary

`D = 0.55*PL + 0.45*AT`

Always keep `(PL,AT)` visible. `D` is only a summary.

Also report:

`(C_sem, C0, R, FHL, PCI, SA, N_A)`

## 18. Required authoring record for each accepted level

1. board size + exact starting layout;
2. dataset + report goals;
3. Report target modes;
4. formula inventory/start positions;
5. explicit legal no-REF route;
6. `C_sem`, `C0`, `B`, `R`;
7. `F_act`, `F_move`, `F_extract`, `F_delivery`, `F_tax`, `FHL`;
8. meaningful formula placement alternatives / PCI;
9. spill/workspace notes;
10. dependency/order graph in prose;
11. anomaly F/A/Resp + observed first spawn/intent traces;
12. critical entities, rough U/T/Slack where pressure matters;
13. post-playtest actual actions/replans/restarts;
14. verdict: keep / tune / redesign.

The model exists to focus playtests, not replace them.
