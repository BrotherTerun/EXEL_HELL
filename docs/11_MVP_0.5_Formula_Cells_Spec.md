# EXEL HELL — MVP 0.5 Formula Cells Specification

Status: approved design specification for implementation after MVP 0.4.

## 1. Goal

MVP 0.5 replaces toolbar/context-menu `SUM` and `SORT` actions with fixed formula cells that exist directly on the worksheet.

The design goal is to make spreadsheet operations part of worksheet space without adding a new player verb, without forcing CUT/PASTE delivery of whole ranges, and without increasing the minimal action cost of simple report goals.

Core input loop:

- selection is free and does not spend a turn;
- select a key or numeric range;
- activate the appropriate formula cell;
- successful formula execution spends one turn.

No formula typing, formula creation, formula editing, or explicit `REF` action is introduced.

## 2. Data model: field and token are separate entities

A worksheet coordinate owns a field/cell object. A field may contain a token, but the field and token are not the same entity.

### Field

A field is identified by worksheet coordinates `(X, Y)` and owns spatial/infrastructure properties.

For MVP 0.5, a field may have one of these formula properties:

- none;
- `SUM`;
- `SORT`.

The formula property belongs to the coordinate and remains there when its current token is removed.

The field property determines:

- how the cell is displayed;
- whether it can accept a selected argument;
- what operation is performed when activated;
- for `SORT`, the fixed spill direction.

### Token

A field may contain zero or one token.

Tokens preserve the current prototype semantics:

- numeric value;
- record key;
- field/parameter key;
- aggregate value;
- semantic links used by SORT/report goals;
- other token-level metadata.

Token properties determine what data the token represents and how operations interact with it.

Field properties and token properties do not overlap.

Example:

- field `(X, Y)` has property `SUM`;
- it currently contains numeric aggregate token `257`;
- the field renders as `=SUM(257)`;
- selecting a range that includes this coordinate exposes numeric token `257` as an operand to another SUM;
- removing token `257` leaves the same field as empty reusable `=SUM()`.

## 3. Formula activation / argument passing

Formula cells do not receive ranges through physical CUT/PASTE.

The current selection is passed as a transient argument when the player activates a formula cell.

This is an implicit reference only for the duration of the action. No persistent reference token or new REF mechanic is created.

Examples of formula-bar representation:

- selected salary key + activate SORT field -> `=SORT(B4)`;
- selected numeric range C2:C6 + activate SUM field -> `=SUM(C2:C6)`.

The player does not type or edit these strings.

A successful formula execution costs one turn. Selection itself costs zero turns.

## 4. `=SUM()` formula field

### Empty state

An empty SUM field renders:

`=SUM()`

It can accept a selected valid numeric range.

### Execution

Input:

- current rectangular selection;
- selection must satisfy the same numeric validity rules as the current SUM unless explicitly changed during implementation/testing.

On successful activation:

1. Numeric operands are read from the selection.
2. Their sum is calculated.
3. Ordinary selected source tokens are consumed/collapsed according to current destructive SUM semantics.
4. The resulting aggregate token is placed inside the activated SUM field.
5. The field now renders as `=SUM(n)`, where `n` is the stored aggregate value.
6. One turn is spent.

### Occupied SUM field

A SUM field containing a token is occupied and cannot execute another SUM into itself.

There is no overwrite mode.

To reuse that formula coordinate, its existing token must first be removed by an allowed token operation such as CUT.

After the token is removed, the field becomes empty `=SUM()` again.

### SUM result as operand

A filled SUM field still contains a normal numeric aggregate token.

Therefore it may be included in the selection passed to another SUM, regardless of distance between the two formula cells, provided the normal range-selection validity rules are satisfied.

The field itself is not consumed by the other SUM.

Its contained token behaves according to token semantics; the formula property remains attached to the coordinate.

### Report fields

A report-result field may itself be a SUM formula field.

This removes the old dual SUM behavior. There is no separate "worksheet SUM" and "report SUM" mode.

The same SUM mechanism executes everywhere:

select range -> activate `=SUM()` -> aggregate is stored in that formula field.

A SUM field located in the protected report area is still mechanically a SUM field; its report role is a separate field property/presentation rule.

This allows simple goals such as Salary Total to remain two actions:

1. select Salary key -> activate SORT;
2. select sorted salary range -> activate report SUM.

## 5. `=SORT()` formula field

### Empty state

An empty SORT field renders:

`=SORT()`

### Input

SORT accepts one selected key token, preserving current semantic categories:

- parameter/field key, e.g. Salary, Hours, Bonus;
- record/instance key, e.g. Ivanov, Petrov.

The key is passed from the current free selection. It does not have to be CUT and physically pasted into the formula field.

### Execution

On successful activation:

1. Resolve the semantic data associated with the selected key using current SORT rules.
2. Physically move the resolved data tokens to the spill area anchored on the SORT field.
3. Store/display the selected key in the SORT field, so the field becomes visually `=SORT(key)`.
4. Spend one turn.

### Spill direction

Spill direction is fixed per SORT field and authored as part of the level layout.

Rules:

- parameter key (`Salary`, `Hours`, etc.) -> associated data are placed in fields below the SORT field;
- record/instance key (`Ivanov`, `Petrov`, etc.) -> associated data are placed in fields to the right of the SORT field.

MVP 0.5 does not dynamically choose another direction to avoid blockage.

If the authored spill direction cannot accommodate the complete result under the current spatial rules, the existing `#SPILL!` failure behavior applies and no successful action is committed.

### Reuse

A SORT field is a coordinate-level formula property, like SUM.

The selected key stored/displayed in the field is a token/content state, not the formula property itself.

Whether/how a filled SORT field is cleared for reuse should follow the same field-vs-token model during implementation; no formula field itself is moved or deleted by CUT/DELETE.

## 6. CUT / PASTE / DELETE interaction

Formula properties belong to fields and cannot currently be moved.

For MVP 0.5:

- CUT can remove an allowed token from a formula field while leaving the formula property at the coordinate;
- after CUT removes a SUM result, `=SUM(n)` becomes `=SUM()`;
- PASTE may place token data only where allowed by the cell/token rules; it does not move or create formula properties;
- DELETE does not destroy formula fields/formula properties;
- the formula itself is never placed into clipboard;
- formula coordinates are not draggable or relocatable by the player.

CUT/PASTE remain spatial correction tools rather than mandatory transport into functions.

Typical uses remain:

- remove an unwanted value from a future SUM range;
- free a SORT spill lane;
- rescue data threatened by `#REF!`;
- reposition data into a valid contiguous range;
- remove a completed aggregate from a formula field so the formula can be reused.

## 7. `#REF!` interaction with formula fields

Formula fields are protected from direct player destruction but are not globally safe from the anomaly.

Required MVP 0.5 rule:

- an empty formula field has the same threat priority as an ordinary empty field;
- once a formula field contains important data, the contained token contributes its normal importance/targeting semantics;
- `#REF!` may destroy/damage a formula coordinate;
- the anomaly should continue to prefer important data rather than formula coordinates merely because they are formulas.

Reason: making all formula cells permanently anomaly-proof would create obvious safe storage during the first 2–3 turns and significantly weaken the threat layer.

Exact implementation of destroyed-formula rendering/state may be chosen during implementation, but the formula coordinate must not be treated as a permanent safe vault.

## 8. Visual states

Minimum required representations:

- empty SUM formula field: `=SUM()`;
- filled SUM formula field: `=SUM(247)`;
- empty SORT formula field: `=SORT()`;
- filled SORT formula field: `=SORT(Зарплата)` / localized equivalent;
- ordinary numeric token: existing plain numeric representation;
- ordinary key token: current blue/key presentation;
- formula field: visually distinct formula-cell background/style;
- report field: light-green background and green border as current report language.

If a report field is also a formula field, report styling and formula content must both remain legible.

Formula-field appearance represents the field property; the text inside the parentheses represents current token/content state.

## 9. Formula bar

Add/readapt the formula bar above the worksheet as a read-only presentation element.

It reflects the currently selected/activated formula state in Excel-like notation, for example:

- `=SUM(C2:C6)`;
- `=SORT(B4)`.

For MVP 0.5 the formula bar is display-only.

The player cannot:

- type formulas;
- edit formulas;
- create new formula cells;
- change field formula properties;
- create persistent references through the formula bar.

The formula bar may later be used for narrative/psychosis presentation, but that is outside the MVP 0.5 core implementation.

## 10. Action economy

MVP 0.5 must not turn formula use into mandatory CUT/PASTE transport.

Required costs:

- selection: 0 turns;
- valid SORT activation: 1 turn;
- valid SUM activation: 1 turn;
- CUT / PASTE / DELETE: retain current turn costs.

Baseline check:

Current simple Salary Total:

1. SORT Salary;
2. SUM Salary into report.

MVP 0.5 equivalent must remain:

1. select Salary key -> activate authored SORT formula field;
2. select resulting salary range -> activate report SUM formula field.

Total: 2 gameplay actions.

Additional turns are acceptable only when they represent actual puzzle decisions, such as rearrangement, clearing a spill lane, saving threatened data, or constructing intermediate aggregates.

## 11. Level-design consequences

Formula coordinates become authored spatial infrastructure.

Their placement should matter because:

- SORT spill geometry originates at a fixed formula coordinate;
- SUM aggregate results physically exist at their formula coordinates;
- intermediate aggregates can become inputs to later calculations;
- `#REF!` may threaten formula coordinates and stored results;
- CUT/PASTE may be required to create valid geometry around authored formula positions.

However, MVP 0.5 must be tested for whether this produces meaningful spatial decisions rather than mere extra cursor travel.

## 12. Report-goal overlap / reusable data

MVP 0.5 must preserve the ability to build multiple report goals from overlapping source data without restoring the old special report-SUM behavior.

Primary mechanism:

- completed SUM fields contain aggregate tokens;
- those aggregate tokens can participate in later SUM selections;
- report SUM fields can therefore serve as protected/committed intermediate totals when level goals form useful dependencies.

Example:

- Goal A: salaries for employees with hours < 40 -> report `=SUM(200)`;
- Goal B: total salary -> later SUM may use the aggregate `200` plus remaining salary tokens.

This makes ordering of report goals part of the puzzle without introducing another function.

Current levels must be reviewed for goal-set compatibility, especially arbitrary partial overlaps that cannot be represented by reusable subtotal dependencies.

## 13. Explicit non-goals for MVP 0.5

Do not add:

- manual formula typing;
- formula creation by the player;
- formula editing;
- explicit REF action/function;
- persistent A1-style reference objects;
- movable formula properties;
- copy/paste of formula cells as formulas;
- dynamic SORT direction selection;
- automatic recalculation chains;
- additional spreadsheet functions;
- new anomaly types as part of this core change.

The purpose of MVP 0.5 is to test formula cells as spatial infrastructure, not to implement Excel.

## 14. Open questions intentionally deferred to playtest/implementation

The following are not considered blockers for the written specification and should be validated in the prototype:

1. Whether fixed formula-cell placement creates meaningful spatial planning or only extra interaction friction.
2. Which existing level goal combinations remain good puzzles under destructive SUM + reusable aggregate dependencies.
3. Exact anomaly behavior/rendering when `#REF!` destroys a formula coordinate.
4. Exact clearing/reuse UX for occupied SORT formula fields, while preserving the field/token separation above.
5. Final formula-cell visual styling and animation; MVP 0.5 only needs unambiguous graybox readability.

## 15. MVP 0.5 acceptance criteria

Implementation is ready for smoke testing when all of the following hold:

- toolbar/context-menu SUM and SORT are no longer required to execute the two core functions;
- authored SUM and SORT cells exist on the board;
- selection -> formula activation works with zero-cost selection and one-turn successful execution;
- SUM always resolves into its activated SUM field;
- occupied SUM cannot be overwritten;
- CUT can remove its aggregate and reveal reusable `=SUM()`;
- filled SUM aggregate can be used by another SUM;
- SORT spills from its formula coordinate in the fixed direction defined above;
- blocked SORT produces `#SPILL!` without committing an invalid result;
- report targets can be SUM formula fields;
- formula fields cannot be moved/deleted by player CUT/DELETE;
- `#REF!` can threaten/destroy formula coordinates according to the anomaly rule above;
- formula bar displays generated formula notation but accepts no input;
- simple Salary Total remains solvable in two gameplay actions before anomaly interference;
- at least one smoke-test level exercises an intermediate aggregate reused by another report goal.
