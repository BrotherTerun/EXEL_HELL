# EXEL HELL — многомерная модель баланса FC2 v2

**Статус: АКТУАЛЬНАЯ модель авторинга/smoke-test.**  
Это не точный решатель. Модель отбрасывает хрупкие раскладки, отделяет полезную нагрузку от налога обслуживания и показывает, что нужно проверять в Unity.

Текущие базовые значения L1–L4 продублированы в `balance/current_level_baselines.csv` и `balance/EXEL_HELL_FC2_Balance_Baselines.xlsx`.

## 1. Базовая стоимость

### `C_sem` — семантическая нижняя граница
Минимум полезных действий для набора целей при благоприятной геометрии и достаточном запасе формул.

Текущие нижние границы:
- SalaryTotal: 2;
- OvertimeTotal: 2;
- BonusTotal: 2;
- BonusAtLeastFour / текущий порог `>=5`: 4;
- SalaryOfMaxOvertime: 3;
- SalaryForHoursBelowForty: 5;
- LowHours + OT Total + Bonus Total: 9.

### `C0` — законный авторский baseline
Минимальное **законное** число действий без REF на точной авторской раскладке.

`C0` берётся из явно записанного маршрута по текущим правилам FC2.

Нет законного маршрута → `C0 = ∞` → уровень недопустим.

### `C_spatial`
Дополнительные полезные действия геометрии/манипуляции сверх семантического минимума и чистого налога формул.

Не насиловать модель ложным точным разложением, если один MOVE выполняет несколько ролей; лучше аннотировать маршрут.

## 2. Режим цели отчёта

Каждая Report Goal должна иметь один режим:
- `DirectValue` — обычная ReportCell, доставить нужный Data-токен;
- `InlineSUM` — ReportCell + SUM, считать прямо в отчёт;
- `PlainDelivery` — обычная aggregate ReportCell; считать в другом месте и MOVE-нуть Aggregate в неё.

`PlainDelivery` — поддерживаемое правило, а не ошибка валидации. Обычно добавляет один MOVE относительно InlineSUM, но освобождает рабочую формулу для повторного использования.

## 3. Formula Handling Load

Записывать:
- `F_act` — полезные активации SUM+SORT;
- `F_move` — MOVE пустой FormulaCell;
- `F_extract` — MOVE occupant наружу ради освобождения формулы;
- `F_delivery` — извлечение, которое одновременно выполняет полезную доставку/постановку результата.

Чистый налог:

`F_tax = max(0, F_extract - F_delivery)`

Нагрузка обслуживания:

`FHL = (F_tax + 0.5*F_move) / max(1,C0)`

Начальные диапазоны:
- `<0.10` лёгкая;
- `0.10..0.20` приемлемая;
- `0.20..0.30` обслуживание формул уже конкурирует с пазлом;
- `>0.30` вероятен редизайн.

### Ограничитель дефицита
Если дефицит формул повышает `C0` более чем примерно на 35% относительно `C_sem` без настоящего решения по размещению/порядку/угрозе — добавить формулы или переделать уровень.

`PlainDelivery`-MOVE, который вынимает Aggregate из SUM и сразу удовлетворяет ReportCell, считается `F_delivery`, а не чистым налогом.

## 4. Выбор размещения формул

Для каждой активации, где позиция важна, определить `P_i` — количество действительно полезных законных позиций формулы.

`PCI = mean(min(P_i,3)/3)`

Интерпретация:
- `0..0.25` почти предопределено;
- `0.25..0.50` ограниченный выбор;
- `0.50..0.75` здоровые альтернативы;
- `>0.75` много альтернатив — проверить, что позиция вообще имеет значение.

Перемещаемая формула с `P_i=1` часто является фиксированной формулой плюс MOVE-tax.

## 5. Давление spill у SORT

Для требуемой SORT `j`:
- `L_j` — длина spill;
- для позиции `p`, `Block_jp` — минимум действий расчистки/ремонта.

`SC_j = min_p(Block_jp)`

`Alt_j = count(p where Block_jp <= SC_j + 1)`

`SP_j = min(1, SC_j / max(1,L_j))`

Диагностика уровня:
- `SP = mean(SP_j)` — степень загромождения;
- `SA = mean(min(Alt_j,3)/3)` — богатство альтернатив.

## 6. Давление MOVE / рабочего пространства

- `M_filter` — обязательные MOVE для фильтрации/расчистки/эвакуации/ремонта геометрии;
- `W_free` — изначально полезные свободные обычные координаты, исключая report/formula/обязательную будущую spill-инфраструктуру;
- `W_peak` — максимум одновременно припаркованных/подготовленных токенов.

`WP = W_peak / max(1,W_free)`

Диапазоны:
- `<0.10` просторно;
- `0.10..0.25` нормально;
- `0.25..0.40` тесно;
- `>0.40` дефицит пространства может начать доминировать.

Для range MOVE считать занятые назначения, а не отдельное staging-состояние на каждый перемещённый токен.

## 7. Зависимости целей

Для каждой цели `g` — набор источников `S_g`.

Для пары `(a,b)`:

`J_ab = |S_a ∩ S_b| / |S_a ∪ S_b|`

Классифицировать отношение:
- independent;
- shared-prep;
- ordered;
- report-mediated;
- hard-conflict.

`report-mediated` означает, что occupant ReportCell может удовлетворить одну цель, а затем постоянно читаться другой SUM.

Hard-conflict → `C0=∞`, пока не изменена раскладка/порядок/инфраструктура.

## 8. Время жизни критичных сущностей

Критический набор `E` может включать:
- сырой Data-токен;
- key;
- aggregate;
- занятую FormulaCell с критичным occupant;
- пустую FormulaCell, которая понадобится позже;
- критичную spill/staging-зону.

Для каждого `e`:

`U_e` = последнее действие baseline-маршрута, к которому сущность должна оставаться доступной.

## 9. Приход угрозы

Оценка наиболее раннего правдоподобного контакта аномалии:

`T_e = F + P_e`

где `F` — задержка первого очага, `P_e` — оценка маршрута/контакта с учётом геометрии.

Также фиксировать прямую допустимость очага `O_e`, если релевантно.

Не считать `T_e` точным без трассы Unity: выбор спавна динамический и зависит от текущего положения критичных токенов.

## 10. Slack / подверженность

`S_e = T_e - U_e`

Интерпретация:
- `>=3` комфортно;
- `1..2` управляемо;
- `0` граница решения;
- `-1..-2` вероятна вынужденная реакция;
- `<=-3` кандидат на перегрузку.

Для уровня:
- `S_min = min(S_e)`;
- `Q = count(S_e <= 1) / |E|`.

Диапазоны exposure:
- `<0.20` низкая;
- `0.20..0.40` лёгкая;
- `0.40..0.65` сильная;
- `>0.65` системная.

## 11. Запас восстановления

`B` = бюджет ходов.

`R = B - C0`

Рабочие диапазоны:
- `R>=5` щедрый;
- `R=3..4` нормальный;
- `R=2` тесный;
- `R<=1` хрупкий.

Уровень, обучающий угрозе, обычно должен оставлять минимум одно понятное восстановительное действие.

## 12. Ритм аномалии

Пусть:
- `F` — первый outbreak;
- `A` — задержка активного outbreak;
- `Resp` — задержка respawn;
- `C0` — baseline действий.

Приблизительное число окон outbreak за baseline:

`N_A = 0`, если REF отключён или `C0 < F`.

Иначе:

`N_A = 1 + floor((C0 - F) / max(1,A))`

`AP = min(1, N_A/3)`

Это окна outbreak, а не число каждого spread intent. Активные Corrupted-клетки могут создавать дополнительные решения между окнами.

## 13. Тяжесть потери/восстановления

`K_e` = минимум дополнительных действий после угрозы/потери для восстановления законного маршрута.

Примеры FC2:
- упреждающий MOVE сырого токена: ~1;
- эвакуация пустой FormulaCell: ~1;
- занятая FormulaCell + эвакуация occupant: до ~2;
- пересчитываемый aggregate: стоимость маршрута пересчёта;
- уничтоженный незаменимый сырой обязательный токен: ∞;
- уничтоженная единственная обязательная формульная инфраструктура: потенциально ∞.

`KS = mean(min(K_e,4)/4)` для конечных значений.

Любой `K_e=∞` при `S_e<=1` — предупреждение о катастрофической подверженности.

## 14. Puzzle Load

`C_n = min(1,C0/12)`

`M_n = min(1,M_filter/5)`

`PL = 100 * (0.45*C_n + 0.15*SP + 0.15*M_n + 0.10*DI + 0.10*WP + 0.05*FHL)`

Диапазоны:
- 0..25 tutorial/light;
- 26..45 normal;
- 46..65 involved;
- 66+ high load.

`PCI`/`SA` — диагностические ограничители дизайна, а не прямые веса сложности.

## 15. Anomaly Threat

`SN = clamp((2-S_min)/5,0,1)`

`OR = count(O_e=1)/|E|`

`AT = 100 * (0.30*SN + 0.25*Q + 0.15*AP + 0.15*KS + 0.15*OR)`

Диапазоны:
- 0..20 декоративная;
- 21..40 лёгкая;
- 41..60 активное тактическое давление;
- 61..80 тяжёлая;
- 81+ хаотическая/катастрофическая.

Не публиковать точный AT новой раскладки без наблюдения реального поведения spawn/intent в Unity. Из предположительных `T_e` очень легко получить ложную точность.

## 16. Сводная оценка

`D = 0.55*PL + 0.45*AT`

Всегда показывать `(PL,AT)` отдельно. `D` — только сводка.

Также сообщать:

`(C_sem, C0, R, FHL, PCI, SA, N_A)`

## 18. Обязательная запись авторинга принятого уровня

1. размер поля + точная стартовая раскладка;
2. dataset + report goals;
3. режимы Report target;
4. запас/стартовые позиции формул;
5. явный законный no-REF маршрут;
6. `C_sem`, `C0`, `B`, `R`;
7. `F_act`, `F_move`, `F_extract`, `F_delivery`, `F_tax`, `FHL`;
8. осмысленные альтернативы размещения / PCI;
9. заметки spill/workspace;
10. граф зависимостей/порядка в прозе;
11. F/A/Resp аномалии + наблюдаемые первые spawn/intent trace;
12. критичные сущности и примерные U/T/Slack там, где важно давление;
13. фактические действия/replan/restart после плейтеста;
14. вердикт: keep / tune / redesign.

Модель нужна для фокусировки плейтестов, а не для их замены.
