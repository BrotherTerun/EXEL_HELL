# EXEL HELL — история тестов и актуальные гейты валидации

**Статус: АКТУАЛЬНАЯ интерпретация исторических данных.**  
Сырые протоколы в `tests/` сохраняются без изменений.

## 1. Почему старые тесты всё ещё полезны

Механики сильно изменились от MVP 0.3/0.4 к FC2, поэтому старые числа ходов и оценки кнопок не могут напрямую валидировать текущую сборку.

Но они выявили повторяющиеся проблемы дизайна:
- аномалия, приходящая после того, как полезные данные уже не нужны, является декоративной;
- повторяющиеся стартовые SORT превращаются в рутину;
- семантические цели интереснее в композиции, чем как отдельная арифметика;
- пересекающиеся цели могут давать полезные зависимости или структурные конфликты;
- детерминированная телеграфия понятна и должна сохраняться;
- CUT/PASTE превратился в повторяющийся налог действий;
- DELETE естественно полезен только при реальном пространственном давлении;
- читаемость обучения/целей отчёта сильно влияет на воспринимаемую сложность.

## 2. MVP 0.2 → семантические данные

Ранний прототип доказал работоспособность базовых манипуляций листом, но показал два провала:
- один DELETE мог фактически закончить угрозу REF;
- имена/числа были в основном декорацией, а не значимыми данными.

Это привело к постоянным outbreak и семантическим Report Goals в MVP 0.3.

## 3. Математическая находка MVP 0.3

Баланс ввёл:
- Base Cost `C`;
- грубый threat horizon `H`;
- последний момент использования данных `U_i`;
- приход угрозы `T_i`;
- Slack `T_i-U_i`.

Ключевой вывод:

> Не спрашивать, интересен ли REF в конфигурации, где мирная задача математически заканчивается раньше, чем REF вообще способен повлиять на неё.

Принцип остаётся актуальным, хотя стоимость действий FC2 изменилась.

## 4. Smoke MVP 0.3

Smoke 01–08 показали:
- многие комбинации слишком рутинны;
- DELETE и RecordKey SORT часто не используются;
- стартовые FieldKey SORT постоянно ощущаются рутиной;
- REF часто меняет только порядок, а не стратегию.

### Smoke-test 09
`SalaryTotal + OvertimeTotal + BonusTotal`, 8 ходов в той сборке.

Динамический REF заставил сразу менять порядок/эвакуировать данные вместо привычного «SORT всё, потом SUM всё». Это был один из первых убедительных примеров давления.

### Smoke-test 10
`SalaryForHoursBelowForty + OvertimeTotal + BonusTotal`, 14 ходов.

Наблюдения:
- первое естественное использование DELETE для контроля REF;
- геометрия/порядок реально нарушались;
- давление REF оценивалось заметно выше простых тестов.

Это подтвердило, что основа encounter — композиция целей + угроза, а не одна сложная формула.

## 5. Данные MVP 0.4

MVP 0.4 исправил:
- exploit одноячеечного SUM;
- защиту отчёта;
- свежие данные;
- часть конфликтов пересечения целей;
- проблемы telegraph/UI.

Smoke 11–15 всё ещё показывали слабое влияние REF в ряде конфигураций и повторяющийся налог «сначала SORT». Clipboard relocation тоже оставался рутиной.

Это помогло обосновать FormulaCells вместо очередного усиления таймингов аномалии.

## 6. Внешние четырёхуровневые плейтесты до FC2

### Player 1
- L1 2:34, первая попытка; ясность задачи 3; просил tutorial;
- L2 влияние REF 4, ясность REF 5, напряжение 2;
- L3 6:01, 5 рестартов; перестройка данных сильная, альтернатив мало; низкое желание переигрывать.

### Player 2
- L1 ясность задачи 2 при интересе к самой табличной задаче;
- L2 влияние REF 5 / ясность 5, напряжение 2;
- L3 перестройка 5, альтернативы 2, replay desire 2; DELETE не использован;
- L4 был испорчен багом, упростившим уровень; влияние REF 1 и почти нет реального риска поражения.

Общий вывод:
- сама телеграфия понятна;
- onboarding/report context требовал улучшения;
- угроза не всегда давала несколько разумных ответов;
- церемония перемещения/инструментов вредила replay value.

Не использовать точные рейтинги этих тестов как acceptance scores FC2.

## 7. Переход к FormulaCells

Первое предложение FormulaCell всё ещё рассматривало позиции формул главным образом как фиксированную инфраструктуру активации. FC2 ввёл:
- Drag=MOVE;
- Shift+Drag=SELECT;
- активацию формулы через DROP;
- перемещаемые пустые FormulaCells;
- range MOVE;
- постоянные Report operands.

Это напрямую убирает старый налог CUT/PASTE и фиксированной панели, сохраняя семантическое/пространственное планирование.

## 8. Что действительно валидировано сейчас

Внутренней реализацией/smoke reasoning подтверждено:
- существует грамматика действий FC2;
- работает движение формул/слои occupant;
- работает постоянство отчёта;
- исправлены blocker'ы отрисовки REF telegraph;
- существует архитектура dynamic spawn/report protection;
- текущие уровни имеют явные законные no-REF baseline routes в docs/code.

**Старые внешние профили честно не валидируют:**
- финальную ясность onboarding FC2;
- replay desire FC2;
- является ли текущий дефицит формул интересным, а не налогом;
- финальное давление поздних уровней после constructor-redesign;
- gameplay психоза;
- читаемость финального pixel-UI/chat/narrative.

Не писать «external playtest confirms FC2», пока реально не протестирована актуальная сборка.

## 9. Текущие технические smoke-gates

### Scene/application
- production boot начинается с Menu;
- New Game → L1 Gameplay;
- Continue/Load → сохранённый уровень Gameplay;
- нет вспышки старого worksheet/tutorial;
- Pause/Resume сохраняют пазл;
- Reset загружает авторский старт;
- Main Menu загружает Menu.

### Constructor
- LevelConstructor открывает авторское поле;
- F2 скрывает/показывает панель без включения turns/REF;
- обычный drag token/formula отражается в Export;
- Export → clipboard → Import восстанавливает layout/goals/parameters;
- runtime Aggregate не запекается в TokenLayout.

### Правила FC2
- invalid drop = 0 действий;
- range MOVE корректен;
- occupied formula сначала отдаёт occupant;
- empty formula перемещается;
- направление SORT/blocked spill корректны;
- SUM поглощает обычные operands, но сохраняет числовые operands ReportCell;
- обычная aggregate ReportCell принимает доставленный Aggregate;
- aggregate ReportCell без SUM не создаёт ложного warning;
- интерфейс отчёта защищён;
- spawn и spread telegraph одновременно читаемы.

## 10. Гейты level design

Для каждого принятого финального уровня:
- явный законный no-REF route и `C0`;
- записан turn reserve `R`;
- проверен Formula Handling Load;
- нет катастрофической подверженности до разумной возможности реакции;
- хотя бы одно предполагаемое решение реально зависит от пространства/порядка/угрозы;
- нет единственного скрытого password-route/hard-lock.

Целевые роли:
- L1 учит FC2 без REF;
- L2 делает REF видимым без требования экспертной защиты;
- L3 вызывает минимум один осмысленный replan;
- L4 допускает несколько ответов на давление и остаётся восстанавливаемым;
- финальная эскалация не должна идти только через рост вычислительной стоимости.

## 11. Вопросы нового внешнего плейтеста FC2

1. Когда стали понятны Drag=MOVE и Shift+Drag=SELECT?
2. Понял ли игрок, что occupied FormulaCell содержит перемещаемый occupant и лежащую под ним переиспользуемую формулу?
3. Перемещал ли FormulaCell намеренно и зачем?
4. Сколько действий сделано исключительно из-за REF?
5. Сколько раз REF менял **маршрут**, а не только порядок?
6. Было ли переиспользование формул очевидным busywork?
7. Ощущалась ли разница PlainDelivery и InlineSUM осмысленной геометрической особенностью?
8. Видел ли игрок больше одного разумного действия в моменты давления?
9. Были ли поражения объяснимыми и обучающими?
10. Хотелось ли после поражения попробовать другой маршрут?

Именно эти ответы вместе с action trace/restarts являются актуальными данными production-core, которые нам нужны.
