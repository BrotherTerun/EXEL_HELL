# EXEL HELL — Formula Cells 2.0 specification v2

**Status: IMPLEMENTED / CORE APPROVED / FROZEN.**  
This document is the canonical FormulaCell specification. It supersedes the first proposal in `11_MVP_0.5_Formula_Cells_Spec.md`.

## Why v2 exists

The first MVP 0.5 proposal used fixed FormulaCells and a free selection → click/activate interaction. Playtests/implementation work showed that this did not create enough direct spatial manipulation and could become contrived.

FC2 changed the grammar to:

`Drag = MOVE`  
`Shift+Drag = SELECT`  
`Formula execution = DROP into formula`

Formula properties themselves became movable when empty.

## 1. Layer model

A cell coordinate may contain independent layers:

`Report property + Formula property + Occupant token + Cell anomaly state`

Formula property:
- none;
- SUM;
- SORT.

Occupant:
- Data;
- FieldKey;
- RecordKey;
- Aggregate;
- Label.

Report property is authored infrastructure and remains at the coordinate.

Formula property may move **only while empty**.

## 2. Universal drag priority

When dragging a formula coordinate:

1. if an occupant exists, drag the occupant;
2. formula remains;
3. when formula is empty, drag may move the Formula property itself.

Examples:

`=SUM(247)` → drag 247 → source becomes `=SUM()`.

`=SORT(Зарплата)` → drag Salary key → source becomes `=SORT()`.

There is no separate formula-move tool.

## 3. Selection

`Shift+Drag` creates one rectangular selection.

Selection is free. It is used primarily as the operand payload for SUM and as the source payload for range MOVE.

No Ctrl/disjoint selections.

## 4. Range MOVE

Dragging a movable occupied cell inside a multi-cell selection translates all movable selected token occupants in one action.

- relative positions preserved;
- empty source cells ignored;
- Formula properties do not move with range token payload;
- own moving occupants may overlap their translated source footprint;
- foreign occupants / Formula destinations / non-Normal cells block;
- successful action costs 1 turn.

## 5. SUM FormulaCell

### Empty state
`=SUM()`

### Activation
Select a valid rectangular numeric range, then drag/drop that selected payload onto empty SUM.

Requirements:
- minimum 2 numeric operands;
- numeric Data/Aggregate only;
- empty Normal cells may be inside rectangle and are ignored;
- source cells Normal;
- target formula not inside source selection;
- target empty/available.

### Result
- sum is computed;
- provenance retained;
- ordinary source numeric tokens consumed;
- numeric occupants of ReportCells are persistent operands and survive;
- Aggregate occupant appears inside SUM;
- one action consumed.

### Reuse
Move aggregate occupant out; SUM remains reusable.

If that MOVE delivers aggregate into a plain ReportCell, extraction and useful delivery are the same action.

## 6. SORT FormulaCell

### Empty state
`=SORT()`

### Activation
Drag one FieldKey/RecordKey into empty SORT.

### Direction
- FieldKey → down;
- RecordKey → right;
- no fallback direction.

### Resolution
- semantic group is resolved from schema;
- full spill positions must be legal;
- associated Data tokens move to spill;
- key becomes SORT occupant;
- invalid spill costs no turn;
- successful SORT costs 1 action.

### Reuse
Move key occupant out first. Parking it purely to free SORT is formula handling tax; moving it somewhere useful may not be.

## 7. Formula movement

An empty FormulaCell may be moved to a legal empty coordinate, including an empty ReportCell.

This costs one action.

Formula mobility is not automatically good design. A useful move should change at least one of:
- spill viability;
- SUM geometry/result staging;
- anomaly exposure;
- future route/order;
- action efficiency compared with clearing blockers.

A formula with only one meaningful destination is often just a movable tax.

## 8. Report + Formula composition

Report property and Formula property are independent.

### Aggregate goal / InlineSUM
Report target also owns SUM. Compute directly into it.

### Aggregate goal / PlainDelivery
Report target owns no formula. Compute Aggregate elsewhere and MOVE it into target.

This is valid and deliberately supported to test reduced formula inventory/reuse.

### DirectValue goal
Target should be plain ReportCell. Move required Data token there.

### Invalid/suspicious cases
- aggregate Report target with SORT → warning;
- direct-value Report target with any Formula → warning.

## 9. Persistent Report operands

Any numeric ReportCell occupant is a persistent operand for later SUM:
- it may be included in selected range;
- its value contributes;
- its occupant is not consumed.

This supports ordered/report-mediated goal dependencies without COPY.

Persistence is a ReportCell property, not a special report-SUM rule.

## 10. Formula bar

Read-only/generated.

Examples:
- `=SORT(B1)`;
- `=SUM(B3:B7)`.

Player cannot type/edit/create formulas through it.

## 11. Formula / REF interaction

Formula coordinates are not permanent safe vaults.

`#REF!` threat is determined by board/anomaly rules and current important occupants/geometry. Formula telegraph presentation must remain readable.

Current telegraph layer is drawn above complete FormulaCell presentation:
- spawn amber translucent + border;
- spread red translucent;
- no raycast interception.

## 12. Legacy toolbar compatibility

Formula levels do not use the old toolbar SUM/SORT/CUT/PASTE grammar. Compatibility layer hides obsolete buttons/tutorial assumptions.

DELETE/SUBMIT/RESET remain until final UI replaces their presentation.

## 13. Action economy acceptance

Required invariants:
- free selection;
- single/range MOVE = 1;
- formula MOVE = 1;
- SORT = 1;
- SUM = 1;
- invalid = 0;
- DELETE = 1.

Simple report tasks should not inflate purely because formulas exist.

Example with adequate infrastructure:

`SORT Salary → SUM Salary` = 2 actions.

A plain ReportCell variant may be 3 (`SORT → workspace SUM → delivery`) because it intentionally trades a dedicated report SUM for reusable formula infrastructure.

## 14. Frozen non-goals

FC2 does not add:
- formula typing/editing;
- persistent A1-reference objects;
- COPY formula semantics;
- automatic recalculation chains;
- dynamic SORT direction;
- new spreadsheet functions;
- manual REF action;
- arbitrary formula creation by player.

## 15. Authoring guardrail

Formula scarcity is a level-design variable, not a goal by itself.

Compare each scarce variant against sufficient infrastructure:
- `C_sem`;
- exact legal `C0`;
- `FHL`;
- placement alternatives;
- recovery reserve under REF.

If scarcity adds >~35% action cost without meaningful placement/order/threat choice, increase formula inventory or redesign.
