# EXEL HELL — MVP 0.3

## Главная проверяемая гипотеза

MVP 0.1 проверяет пространственное преобразование таблицы. MVP 0.2 должен сделать порядок данных после SORT читаемым через положение ключей записей/параметров. MVP 0.3 проверяет следующий слой:

> Игроку должно быть важно не только **где лежит токен**, но и **что именно этот токен означает и какое значение содержит**.

Сейчас `Иванов`, `Зарплата` и `123` можно заменить на `Объект1`, `Категория1` и `a` почти без потери gameplay. В MVP 0.3 это должно перестать быть верно.

## Три слоя смысла данных

Каждый DataToken рассматривается одновременно как:

1. **Identity** — к какой записи и параметру он принадлежит (`recordId`, `fieldId`).
2. **Value** — какое фактическое число/текст он содержит; значение может участвовать в условиях отчёта.
3. **Lineage / provenance** — из каких исходных токенов получен результат после SUM/других преобразований.

Положение на поле остаётся отдельным пространственным состоянием и не определяет семантическую принадлежность.

## ReportGoal как правило, а не только ожидаемое число

`SUBMIT` не должен проверять только совпадение итогового числа. Иначе произвольный набор значений, случайно дающий ту же сумму, считается правильным.

В MVP 0.3 ReportGoal должен уметь проверять:
- итоговое значение;
- допустимый набор/условие исходных токенов;
- при необходимости тип результата (прямое значение или AggregateToken).

`AggregateToken` после consuming SUM сохраняет список/набор `SourceTokenIds` либо эквивалентное описание provenance.

## Минимальные архетипы задач MVP 0.3

### A. Полная агрегация параметра
Пример: `Итого зарплата`.

Нужно собрать все `fieldId = salary` и получить корректный aggregate.

Это базовая задача и контрольная точка относительно MVP 0.1.

### B. Условная агрегация по фактическому значению
Пример: `Сумма премий >= 4`.

При текущем dataset правильные источники:
- Иванов: 5
- Волкова: 4
- Ким: 6

Правильный ответ: **15**.

Игрок должен прочитать значения, выбрать только удовлетворяющие условию токены и при необходимости пространственно собрать их в диапазон перед SUM. Здесь конкретные числа впервые реально меняют решение.

### C. Поиск значения через связь двух параметров
Пример: `Зарплата сотрудника с максимальной переработкой`.

Текущий dataset:
- максимальная переработка = Сидоров, 5;
- зарплата Сидорова = **41**.

Задача требует сначала понять один параметр, определить запись, затем найти связанное значение другого параметра. Это проверяет, что фамилии/параметры — не декоративные подписи.

Для этого MVP 0.3 опирается на читаемую пространственную связь после SORT, закладываемую в MVP 0.2.

## Почему не добавляем полноценный parser ради этого

Цель MVP 0.3 — проверить ценность содержания данных, а не симулировать Excel целиком.

Допустимо оставить текущие операции (`SORT`, `SUM`, `CUT`, `PASTE`, `DELETE`) и расширить:
- правила ReportGoal;
- provenance AggregateToken;
- условия задач;
- читаемость соответствия записей и параметров.

Новые формулы (`IF`, `FILTER`, `COUNTIF` и т.п.) добавляются только если после этой проверки видно, что они создают новые типы решений, а не просто сокращают существующие цепочки.

# `#REF!` в MVP 0.3 — постоянная угроза

## Проблема MVP 0.1

Сейчас `DELETE` первой заражённой клетки полностью прекращает угрозу: активных `#REF!` больше нет, а новая вспышка не создаётся.

Это превращает карантин в одноразовую кнопку выключения аномалии.

## Новое правило

`DELETE` уничтожает **локальный очаг**, но не саму систему аномалии.

Пока уровень не завершён, AnomalyController продолжает создавать новые вспышки по заданному расписанию/правилу.

Минимальная модель MVP 0.3:

1. Есть ограниченное число вспышек на уровень, например `3`.
2. Первая появляется по `initialActivationTurn`.
3. Если все активные `#REF!` были уничтожены/изолированы, через `respawnDelayTurns` публикуется новый Spawn Intent.
4. Spawn Intent заранее показывает клетку будущего появления, как и обычный Anomaly Intent.
5. После задержки новая клетка становится `Corrupted` и начинает распространяться.
6. Точки появления выбираются детерминированно из списка/seed, чтобы уровень можно было балансировать и повторно тестировать.
7. `DELETE` остаётся полезным: он покупает время и меняет геометрию поля, но не снимает давление до конца уровня.

## Параметры для балансировки

В конфиг/level data для MVP 0.3 вынести:
- `maxOutbreaks`;
- `initialActivationTurn`;
- `respawnDelayTurns`;
- список/правило spawn points;
- `corruptionTurnsBeforeDestroy`;
- при необходимости `maxSimultaneousOutbreaks`.

## Требование fairness

Новый spawn не должен быть скрытым RNG.

Если следующая вспышка уже запланирована, игрок заранее видит:

`НОВЫЙ #REF! → F6 через 1 ход`

Таким образом игрок решает известную задачу: закончить расчёт, эвакуировать данные или заранее освободить/изолировать область.

# Критерий успеха MVP 0.3

Прототип проходит проверку, если одновременно выполняются три условия:

1. Игроку приходится читать фактические значения/семантику данных, а не только их координаты.
2. Два численно одинаковых результата, полученных из разных семантических источников, могут различаться по корректности отчёта.
3. `#REF!` нельзя навсегда выключить одним ранним DELETE; карантин остаётся локальным временным решением.
