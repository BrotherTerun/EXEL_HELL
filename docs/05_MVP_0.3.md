# EXEL HELL — MVP 0.3

## Главная проверяемая гипотеза

MVP 0.1 проверяет пространственное преобразование таблицы. MVP 0.2 должен сделать порядок данных после SORT читаемым через положение ключей записей/параметров. MVP 0.3 проверяет следующий слой:

> Игроку должно быть важно не только **где лежит токен**, но и **что именно этот токен означает и какое значение содержит**.

Сейчас `Иванов`, `Зарплата` и `123` можно заменить на `Объект1`, `Категория1` и `a` почти без потери gameplay. В MVP 0.3 это должно перестать быть верно.

## Три слоя смысла данных

Каждый DataToken рассматривается одновременно как:

1. **Identity** — к какой записи и параметру он принадлежит (`recordId`, `fieldId`).
2. **Value** — какое фактическое число/текст он содержит; значение может участвовать в условиях отчёта.
3. **Lineage / provenance** — из каких исходных токенов получен результат после SUM/других преобразований.

Положение на поле остаётся отдельным пространственным состоянием и не определяет семантическую принадлежность.

## Проверка ReportGoal

В основном MVP `SUBMIT` проверяет **только итоговое числовое значение** в целевой клетке.

Это сознательное правило: для начальника важен полученный результат, а не то, каким способом сотрудник к нему пришёл. Случайно полученный правильный ответ тоже принимается.

При этом `AggregateToken` после consuming SUM продолжает хранить `SourceTokenIds` / provenance. Эти данные пока не влияют на победу и сохраняются как основа для возможной отдельной механики:
- проверка качества отчёта;
- аудит;
- скрытая концовка/квест;
- оценка «правильности метода» отдельно от формального результата.

## Минимальные архетипы задач MVP 0.3

### A. Полная агрегация параметра
Пример: `Итого зарплата`.

Нужно получить итог **247**.

### B. Условная агрегация по фактическому значению
Пример: `Сумма премий >= 4`.

При текущем dataset подходящие значения:
- Иванов: 5
- Волкова: 4
- Ким: 6

Правильный ответ: **15**.

Игрок должен прочитать значения и понять условие. SUBMIT при этом проверяет число 15, а не происхождение результата.

### C. Поиск значения через связь двух параметров
Пример: `Зарплата сотрудника с максимальной переработкой`.

Текущий dataset:
- максимальная переработка = Сидоров, 5;
- зарплата Сидорова = **41**.

Задача требует понять один параметр, определить запись, затем найти связанное значение другого параметра.

### D. Условие через один параметр, агрегация другого
Пример: `Зарплаты сотрудников с часами < 40`.

Под условие попадают Сидоров (32) и Ким (36). Их зарплаты: 41 + 55 = **96**.

## Почему не добавляем полноценный parser ради этого

Цель MVP 0.3 — проверить ценность содержания данных, а не симулировать Excel целиком.

Оставляем текущие операции:
- `SORT`;
- `SUM`;
- `CUT`;
- `PASTE`;
- `DELETE`.

Новые формулы (`IF`, `FILTER`, `COUNTIF` и т.п.) добавляются только если видно, что они создают новые типы решений, а не просто сокращают существующие цепочки.

# `#REF!` в MVP 0.3 — постоянный процесс распада

## Принцип

`#REF!` нельзя победить полностью.

`DELETE` уничтожает **конкретный локальный очаг**, но система аномалии продолжает работать до окончания уровня.

## Scheduler вспышек

1. Первая вспышка планируется через `anomalyActivationTurn`.
2. Spawn Intent заранее показывает клетку и число оставшихся ходов.
3. После появления очаг начинает работать по существующему AI `#REF!`.
4. Если игрок полностью уничтожил все активные очаги, следующий spawn рассчитывается заново и появляется через `respawnDelayTurns`.
5. Если игрок НЕ уничтожает существующие очаги, новые вспышки всё равно продолжают планироваться через `outbreakDelayWhileActiveTurns`.
6. Таким образом на поле могут одновременно существовать несколько очагов.
7. Количество вспышек не ограничено.

## Динамический выбор spawn cell

Статического списка spawn points нет.

При планировании новой вспышки система:
1. определяет клетки с данными, важными для выбранных Report Goals, и report cells;
2. ищет доступные Normal-клетки поблизости;
3. не выбирает саму клетку с критичными данными или report cell;
4. предпочитает расстояние `spawnPreferredDistance` с допуском `spawnDistanceVariation`;
5. среди лучших кандидатов детерминированно ротирует несколько вариантов (`spawnCandidatePoolSize`), чтобы вспышки не возникали всё время в одной точке.

Это не скрытый RNG: конкретная клетка показывается игроку заранее через Spawn Intent.

Если игрок уничтожил/заблокировал будущую spawn-cell до срабатывания Intent, аномалия не телепортируется мгновенно в другую точку: выбирается новая позиция и заново показывается короткий telegraph.

## Параметры Inspector

- `anomalyActivationTurn` — задержка первой вспышки;
- `respawnDelayTurns` — пауза после полной зачистки активных очагов;
- `outbreakDelayWhileActiveTurns` — интервал новых вспышек, пока старые всё ещё живы;
- `corruptionTurnsBeforeDestroy` — время жизни заражённой клетки;
- `spawnPreferredDistance` — желаемая дистанция от приоритетных данных;
- `spawnDistanceVariation` — допустимое отклонение;
- `spawnCandidatePoolSize` — размер набора лучших позиций для детерминированной ротации.

# Критерий успеха MVP 0.3

Прототип проходит проверку, если одновременно выполняются условия:

1. Игроку приходится читать фактические значения/семантику данных, а не только их координаты.
2. Разные Report Goals требуют заметно разных цепочек действий.
3. `#REF!` нельзя навсегда выключить одним ранним DELETE.
4. Игнорирование существующего очага не выключает давление: через некоторое время появляются дополнительные очаги.
5. Spawn остаётся телеграфированным и детерминированным, поэтому давление не превращается в скрытый RNG.
